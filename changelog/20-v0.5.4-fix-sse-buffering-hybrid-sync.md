# Changelog 20: v0.5.4 - Fix Cloudflare Quick Tunnel SSE Buffering & Hybrid Snapshot Sync

## 1. Bối cảnh & Hiện tượng (Incident Context)
Người dùng báo cáo khi chạy Cloudflare Quick Tunnel (`*.trycloudflare.com` - Domain ngẫu nhiên), đầu phát (`*-s`) và đầu nhận (`*-r`) không đồng bộ được dữ liệu mặc dù cùng chung room:
- Trên Web phát (`*-s`), người dùng nhập nội dung và bấm lưu thành công (`[POST] /<room>-s 200 OK`).
- Khi mở Web nhận (`*-r`), trình duyệt hiển thị giao diện Web SPA nhưng nội dung luôn bị kẹt ở trạng thái `# Chờ dữ liệu từ TX...`, hai đèn trạng thái `TX ○` và `RX ○` không sáng chấm đen (`●`).
- Khi sử dụng Custom Domain (`s0.wd.io.vn`) qua Named Tunnel thì lại hoạt động bình thường.

## 2. Nguyên nhân Gốc rễ Chính xác (Root Cause Analysis - Proven by Forensic Probe)
Qua kiểm tra đo đạc trực tiếp trên gói tin TCP/SSL thô kết nối vào Cloudflare Edge (`HKG edge`):
1. **Cloudflare Quick Tunnel Buffer Lock trên Chunked Streams:**
   - Trên cụm máy chủ công cộng ẩn danh `*.trycloudflare.com`, Cloudflare NGINX Edge proxy bắt buộc kích hoạt bộ đệm nén (Compression Buffering) đối với mọi kết nối HTTP/1.1 có `Transfer-Encoding: chunked`.
   - Trong phiên bản cũ, server thiết lập header không hợp chuẩn `Content-Encoding: none` và chỉ gửi 2048 bytes padding.
   - Do đó, Cloudflare Edge giữ lại 100% dữ liệu luồng SSE trong bộ đệm và **không trả về bất kỳ body byte nào** cho trình duyệt (curl timeout sau 5000ms với 0 bytes received).
   - Trình duyệt ở phía Receiver bị kẹt vô hạn ở trạng thái `readyState: 0 (CONNECTING)` của `EventSource`, không bao giờ nhận được sự kiện `event: init` để hiển thị dữ liệu ban đầu.
   - Ngược lại, Custom Domain sử dụng Named Tunnel có cấu hình HTTP/2 gRPC/Multiplexing riêng trên Cloudflare Dashboard nên không bị bộ đệm này giữ lại.
2. **Thiếu Dữ liệu Snapshot trong Pre-check HTTP:**
   - Web SPA gọi `GET /<room>/events?check=1` trước khi mở SSE nhưng server chỉ trả về `{"status":"ok"}` rỗng, bỏ lỡ cơ hội chuyển giao dữ liệu payload trực tiếp qua HTTP response thông thường (vốn không bao giờ bị đệm bởi proxy).

## 3. Giải pháp Khắc phục Triệt để (Architectural Resolution)
Áp dụng mô hình **Hybrid Sync (HTTP Snapshot tức thì + SSE Realtime Stream + Fallback Heartbeat Polling)**:
1. **Payload Snapshot trong HTTP Check:**
   - Khi frontend gọi `GET /<room>/events?check=1`, server trả về toàn bộ dữ liệu hiện tại của phòng:
     `{"status":"ok", "slug":..., "slot_type":..., "slot_text":..., "slot_file_name":..., "slot_file_size":..., "sender_paired":..., "receiver_paired":...}`.
   - Frontend `app.js` lập tức gọi `renderPayload(d)` và `setPairStatus(...)` ngay khi nhận được phản hồi HTTP (độ trễ 0ms mà không cần đợi SSE).
2. **Fallback Polling Chu kỳ 3 giây:**
   - Frontend kích hoạt `startPolling` định kỳ 3 giây gửi request kiểm tra trạng thái nhẹ (~150 bytes). Nếu SSE bị nhà mạng, proxy trường học/doanh nghiệp hoặc CDN giữ lại, hai đầu dây vẫn đồng bộ mượt mà 100%.
3. **Phá Bộ đệm Chuẩn hóa SSE Headers:**
   - Đổi `Content-Encoding: identity` theo chuẩn RFC 9110.
   - Tăng dung lượng padding comment lên **4096 bytes** (`strings.Repeat(" ", 4096)`).
4. **Cloudflare Edge Warmup Verification:**
   - Trong `host.go`, tiến trình tự động thực hiện ping kiểm tra `/health` tới Cloudflare Edge trước khi hiển thị bảng URL, loại trừ hoàn toàn hiện tượng người dùng click sớm khi DNS toàn cầu chưa kịp trỏ IP (DNS propagation race condition).
